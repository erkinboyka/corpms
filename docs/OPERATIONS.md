# Эксплуатация и выпуск

## Подготовка окружения

- Document root — только `public/`; `.env`, `storage/app`, журналы и backup недоступны через HTTP.
- HTTPS, `APP_ENV=production`, `APP_DEBUG=false`, корректный `APP_URL`, защищённые cookies. Часовой пояс приложения и компаний согласовать с правилами учёта.
- Раздельные БД, ключи, файловые хранилища и интеграции для development/test/staging/production.
- Пользователь приложения получает необходимые права на свои таблицы; права CREATE/DROP DATABASE нужны только отдельному процессу проверки, не обычному приложению.
- Доступ на запись — к storage и bootstrap/cache. Исходники не должны быть доступны для записи web-пользователю.
- Сохранить APP_KEY в защищённом резервировании. Утрата ключа означает невозможность расшифровать сохранённые ключи интеграций.

## Выпуск

1. Зафиксировать версию и состав изменений; проверить CI, матрицу требований и открытые P0/P1.
2. На staging с копией структуры/обезличенных данных проверить миграции вперёд и совместимость предыдущей версии приложения.
3. Создать backup БД, файлов вложений и конфигурации/APP_KEY; проверить доступность копий и место.
4. При несовместимом изменении схемы включить обслуживание `php artisan down`; остановить обработку мутаций и дождаться завершения задач. Процедура без простоя пока не подтверждена.
5. Установить зависимости `composer install --no-dev --optimize-autoloader`, выполнить `php artisan migrate --force`, затем `php artisan config:cache` и `php artisan view:cache`.
6. Перезапустить процессы очереди (`php artisan queue:restart`) и долгоживущие HTTP workers, если они используются.
7. Выполнить `php artisan corpms:health --json`, проверить вход, права, чтение/запись документа, задачу и обработку очереди на специально выделенных проверочных данных.
8. Выключить обслуживание `php artisan up`, наблюдать за ошибками, задержками, очередью и изменениями бизнес-показателей.

Миграции 19.11.2026 изменяют уникальность настроек и шифруют существующие ключи. При дубликатах глобальных настроек миграция останавливается без выбора/удаления значения: конфликт разрешается владельцем данных. Секреты при откате шифрования намеренно остаются зашифрованными. Старую версию без соответствующего accessor возвращать нельзя без подготовленной процедуры совместимости.

## Откат

Сначала определить совместимость предыдущего кода с уже применённой схемой. Откат приложения не равен `migrate:rollback`. Не применять слепой откат миграций на рабочей БД. Возврат первоначальной уникальности настроек запрещён при наличии настроек компаний. При восстановлении backup необходимо остановить записи и учитывать потерю изменений после точки копирования; решение принимает ответственный за выпуск.

## Резервирование и восстановление

`php artisan db:backup --connection=<имя> --keep=14` создаёт консистентную SQLite-копию через VACUUM INTO либо MySQL-дамп. Для MySQL нужен mysqldump в PATH или DB_DUMP_BINARY. Каталог BACKUP_PATH должен быть вне public; хранить копии также вне хоста приложения с шифрованием и ограниченным доступом. Ротация применяется отдельно к каждому имени подключения.

Проверка восстановления выполняется в отдельном окружении:

1. Взять копию БД, вложений и соответствующего APP_KEY; проверить контрольные суммы и время создания.
2. Создать новую пустую БД с другим именем и отдельным пользователем; восстановить туда копию. Для SQLite открыть копию и выполнить `PRAGMA integrity_check`; для MySQL импортировать дамп инструментом администратора в эту отдельную БД.
3. Подключить изолированный экземпляр приложения к восстановленной БД, отключив исходящие интеграции и фоновые задания, способные отправлять сообщения.
4. Проверить контрольные количества сотрудников/документов, суммы платежей, остатки, чтение вложений и расшифровку тестового секрета.
5. Зафиксировать длительность восстановления, возраст последнего восстановленного изменения, ошибки и владельца проверки. Эти измерения определяют достижимые RTO/RPO.

Автотесты подтверждают чтение SQLite-снимка и ротацию. 19.11.2026 локальная MySQL-копия восстановлена в отдельную БД: совпали количества компаний, сотрудников, документов, задач, платежей и движений, а также суммы платежей и количеств склада. Импорт выполнялся отдельным временным пользователем с правами только на проверочную БД; проверочные БД и пользователь удалены. Воспроизводимая команда: `php tools/verify-backup.php <путь.sql> <путь-к-mysql>`.

`php artisan files:backup --json` создаёт ZIP дисков local/public в BACKUP_PATH с манифестом SHA-256. Каталог назначения запрещён внутри public и исходных дисков. Архив перечитывается перед признанием успешным; изменение файла во время копирования приводит к отказу. Для согласованной точки БД/вложений нужно приостановить записи либо использовать согласованные снимки хранилища. Расписание: БД 03:30, файлы 03:40; это отдельные копии, а не атомарный общий snapshot. Для S3 нужен отдельный процесс резервирования провайдера.

`php artisan files:verify <путь.zip> --json` восстанавливает в новую приватную папку storage/framework/restore-check, сверяет размеры и SHA-256, отклоняет небезопасные пути. Рабочие вложения не перезаписываются. 19.11.2026 восстановлены 806 файлов, 1 192 921 байт, все контрольные суммы совпали; локальное время проверки 0,937 с. Это не RTO полного приложения. Пробные копии содержат конфиденциальные данные и требуют той же политики доступа и хранения, что и backup. APP_KEY резервируется отдельно; без него зашифрованные настройки и история восстановления очереди не расшифруются.

Восстановление вне исходного хоста, доставка копий во внешнее хранилище и RPO/RTO под рабочей нагрузкой остаются непроверенными.

Сеансы версионируются: отключение сотрудника и сброс пароля отзывают прежние входы. Возврат сотрудника в active не оживляет прежнюю сессию. При первом обновлении сеансы старого формата потребуют повторного входа.

## Наблюдение

- Запуск scheduler каждую минуту, worker под менеджером процессов с автоперезапуском.
- Оповещение при ненулевом health-check, failed_jobs, росте backlog/возраста старейшей задачи, отсутствии свежего backup, заполнении диска и росте 5xx.
- Отдельные проверки HTTP-доступности, TLS, scheduler heartbeat и активности worker: встроенный health не доказывает их работу.
- Не отправлять в логи пароли, токены, содержимое конфиденциальных документов и строки подключения. Настройки API-ключей сохраняются шифрованными, журналы изменений используют маску.
- Метрики p95/p99 и цели доступности утверждаются на целевой инфраструктуре. Локальная HTTP-проверка: 200 запросов, 4 клиента, один PHP worker, 1022 сотрудника/10000 задач, p95 959,46 мс, p99 1343,81 мс, 0 ошибок. Это ограниченный baseline, не производственный SLO.

## Восстановление AI-очереди

`php artisan corpms:ai-recover --dry-run` перечисляет только известные RetryAiAnswer. Запуск без dry-run повторно отправляет доступные пользователю корпоративные данные настроенному AI-провайдеру, поэтому требует полномочий на такую передачу. Команда перепроверяет права, сохраняет оригинал записи шифрованным на приватном диске и удаляет из очереди только успешно разрешённую запись; неудача оставляет её для диагностики. Обычные задания не очищаются. Сохранять APP_KEY и журнал аудита. При штатном выполнении использовать worker; эта команда предназначена для контролируемого восстановления.
