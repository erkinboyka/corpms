## Подтверждённые проблемы

### 1. P1 — доступ к карточке сотрудника выходит за пределы отдела

- Код: `app/Http/Controllers/Web/EmployeeController.php:134–147`, маршрут `routes/web.php:96`, `EnsurePermission.php:46–54`.
- У роли `department_director` право `employees.view` имеет область `department`. Список сотрудников ограничивает отдел, а `show()` проверяет только принадлежность компании. Middleware проверяет наличие права, но не область целевого объекта. `employees.view_props` также проверяется без сопоставления с отделом сотрудника.
- Воспроизведение: создать два отдела одной компании, директора первого и сотрудника второго; от директора выполнить GET `/employees/{id_сотрудника_второго_отдела}`.
- Ожидание: 403. Факт: **HTTP 200**. Это полноценная HTTP-проверка со штатными middleware.
- Последствие: директор получает карточки и разрешённые ему реквизиты сотрудников других отделов через подбор ID. Межтенантный guard этого не предотвращает: компания совпадает.
- Исправление: единая объектная проверка `own/department/company` для карточки, реквизитов и подчинённых; аналогично проверить операции изменения при узких персональных разрешениях.

### 2. P1 — увольнение не прекращает вход и действие прав

- Код: `app/Http/Controllers/Auth/AuthController.php:60`, `app/Support/PermissionService.php:39–127`, `app/Http/Controllers/Web/EmployeeController.php:154–186`.
- Статус `dismissed` сохраняется в карточке, но аутентификация проверяет только email/пароль, а разрешения вычисляются по оставшимся ролям без проверки статуса сотрудника. В web-цепочке нет обязательной проверки активности.
- Воспроизведение: сотруднику с учёткой и ролями установить `status=dismissed`, затем проверить аутентификацию и права новым экземпляром сервиса.
- Факт: **вход по прежнему паролю успешен**, `tasks.view` сохраняется. Прямые вызовы штатного механизма Auth и PermissionService; отдельный POST формы входа не выполнялся.
- Последствие: административное увольнение само по себе не отзывает доступ к корпоративным данным.
- Исправление: явно определить политику блокировки inactive/dismissed, проверять её при входе и каждом авторизованном запросе; отзывать существующие сеансы при отключении доступа.

### 3. P1 — повторный приём одной закупки удваивает складской остаток

- Код: `app/Domains/Inventory/Services/InventoryService.php:140–179`, вызов из `PurchaseController::receive()`.
- Статус проверяется на переданном объекте до транзакции. В транзакции заказ не перечитывается с блокировкой; уникального ограничения на оприходование заказа в журнале движений нет.
- Воспроизведение: до выполнения приёма загрузить два независимых объекта одного заказа со статусом `ordered` и позицией 10 единиц; передать каждый в `receive()` последовательно. Это воспроизводит состояние двух запросов, загрузивших заказ до первого коммита, без настоящей параллельной нагрузки.
- Ожидание: второй вызов отклонён, остаток 10. Факт: **оба приняты, остаток 20**.
- Последствие: фиктивное увеличение запасов при пересекающихся запросах на приём.
- Исправление: перечитывать и блокировать заказ внутри транзакции, проверять актуальное состояние; добавить устойчивую защиту от повторного оприходования.

### 4. P1 — календарь другой компании меняет расчёт отпускных часов

- Код: `app/Domains/Payroll/Services/PayrollCalculationService.php:171–176`.
- Праздники выбираются только по периоду, без ограничения `company_id`. Не учитывается и флаг `is_day_off` при выборе исключаемых дней.
- Воспроизведение: отпуск сотрудника компании А на 19.11.2026, расчётный интервал 18–20.11; график отсутствует, норма 8 ч. Добавить выходной праздник на 19.11 только для компании Б и повторить вычисление `paidLeaveHours()`.
- Ожидание: 8 ч в обоих случаях. Факт: **8 → 0 ч**. Вызван реальный расчётный метод через Reflection; вся ведомость в этом воспроизведении не рассчитывалась.
- Последствие: данные одного арендатора влияют на начисления другого.
- Исправление: выбирать только праздники компании сотрудника и явно разрешённые глобальные, учитывать признак выходного. Проверить переносы дней и графики отдельно.

### 5. P2 — объединение ролей выбирает более узкие права

- Код: `app/Support/PermissionService.php:102,112`; корректная шкала определена в `app/Shared/Enums/PermissionScope.php:14–21`.
- Области доступа сравниваются через строковое `value`, а не через `rank()`. Лексикографически `own > department > company`, что противоположно нужному порядку.
- Воспроизведение: сотруднику назначить `employee` и `company_director`, запросить `tasks.view`.
- Ожидание: `company`. Факт: **own**. Аналогичная ошибка есть при объединении персонального override с ролью.
- Последствие: добавление роли способно уменьшить доступ; заявленная модель объединения разрешений нарушена.
- Исправление: сравнивать ранги и проверить сочетания нескольких ролей/override во всех порядках.

### 6. P2 — справочники формы учёток и карточки сотрудника раскрывают данные других компаний

- Код: `app/Http/Controllers/Web/UserController.php:69–73`, отображение в `resources/views/admin/users.blade.php` через `$candidates`; `resources/views/employees/show.blade.php:268,277,286`.
- Кандидаты для привязки учётки выбираются без `company_id`. В карточке сотрудника графики, отделы и должности запрашиваются прямо из шаблона без ограничения компании.
- Воспроизведение: создать сотрудника компании Б без учётки, получить данные `UserController::index()` в контексте компании А. Факт: **сотрудник Б присутствует в candidates**. Шаблон выводит его ФИО и табельный номер. Это проверка данных контроллера, не HTTP-запрос `/users`; маршрут требует `users.manage`.
- Для трёх справочников карточки подтверждена цепочка кода: полный запрос → вывод вариантов формы. Отдельного браузерного воспроизведения не было.
- Последствие: утечка справочной и персональной информации между компаниями. Проверка POST при привязке защищает запись, но не утечку списка.
- Исправление: готовить все справочники в контроллере с обязательным ограничением компании, протестировать содержимое HTML под двумя арендаторами.

## Существенные риски, не воспроизведённые конкурентной нагрузкой

1. **P1, платежи:** `FinanceService.php:151–169` проверяет статус и остаток до транзакции, без блокировки счёта. Два запроса могут одновременно пройти проверку остатка и записать переплату. `cancel()` также не синхронизирован с оплатой. Цепочка кода подтверждена, фактическая гонка на рабочем типе СУБД не запускалась.
2. **P1, списания:** `InventoryService.php:107–110` читает агрегат остатка внутри транзакции, но без блокировки общего ресурса. Два списания могут прочесть один остаток и вместе увести склад в минус. Наличие транзакции само по себе не сериализует эту проверку. Нужна проверка на целевой СУБД.
3. **P2, настройки:** миграция `2026_11_18_140000_add_company_id_to_settings_table.php:19` использует `nullOnDelete()`. Удаление компании может превратить её настройки в глобальные fallback-строки. Составной unique с nullable company_id не обеспечивает единственность глобального значения. Фактический сценарий удаления компании с настройками не воспроизводился.
4. **P2, жизненный цикл прав:** PermissionService зарегистрирован singleton и кэширует роли/разрешения без сброса. Для обычного PHP запросы изолированы; при переходе к долгоживущему HTTP-процессу понадобится отдельная проверка отзыва ролей. Текущий запуск такого сервера не установлен.
5. **P2, увольнение и расчёт:** форма/контроллер изменения сотрудника не задают `fired_at`, тогда как расчёт окончательного начисления требует эту дату для dismissed. Сквозной сценарий увольнение → окончательная ведомость не воспроизводился.
