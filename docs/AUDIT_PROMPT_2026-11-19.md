# Промпт для оценки реализации CorpMS

Для аудита полной BM Systems целевая концепция и требуемая структура из `BM_SYSTEMS_TARGET_SPEC.md` дополняют этот исходный технический промпт. Оценивать по шкале 0–5 отдельно по 22 направлениям, отсутствующему модулю ставить 0; строить карту модулей и связей, приоритеты, целевую архитектуру и следующий спринт. Не смешивать прежний узкий технический балл с полнотой новой концепции.

Проведи независимый аудит текущего рабочего дерева CorpMS. Сначала зафиксируй критерии, затем исследуй реализацию и выполни доступные безопасные проверки. Не исправляй продукт в ходе аудита и не перезаписывай изменения пользователя. Не используй рабочую БД для тестовых операций. Не раскрывай секреты.

## Основание и границы

Определи назначение системы по доступным требованиям, маршрутам, сервисам и тестам. Если ТЗ отсутствует, не делай вывод о проценте выполнения ТЗ. Оцени техническую готовность по наблюдаемым фактам. Текущее дерево, включая незакоммиченные изменения, является объектом аудита. Старые отчёты не являются доказательствами.

## Проверки

1. Функциональность (25%): сквозные сценарии, реальные действия вместо заглушек, обработка ошибок, границы прав и состояний.
2. Безопасность (25%): аутентификация, авторизация каждого действия, область own/department/company, изоляция компаний, файлы и секреты, входящие устройства, опасные выходные данные.
3. Данные и бизнес-правила (20%): транзакции, конкурентные изменения, деньги и остатки, идемпотентность, связи, миграции и переходы состояний.
4. Тестирование (15%): прохождение тестов в изолированной БД, отрицательные сценарии, проверки фактических изменений данных. Количество тестов само по себе не означает качество покрытия.
5. Интерфейс (10%): согласованность шаблонов, формы и ошибки, состояния загрузки, доступность, адаптивность. Без браузерной проверки не заявлять визуальную проверку выполненной.
6. Эксплуатация (5%): воспроизводимая установка, документация, резервирование, очереди, расписание, журналирование и автоматические проверки.

## Доказательства и приоритеты

Разделяй подтверждённые дефекты, риски и непроверенные предположения. Для дефекта укажи файл и строки, предпосылки, воспроизведение или цепочку кода, ожидаемое/фактическое поведение, последствия и рекомендацию. Приоритет P0 — немедленная критическая угроза; P1 — блокер выпуска/существенный ущерб; P2 — значимое ограничение; P3 — улучшение. Не объявляй уязвимость доказанной по одному подозрительному фрагменту: проверь middleware, контроллер, сервис и существующие тесты.

## Оценка

По каждому направлению поставь 0–10 и укажи уверенность и ограничения проверки. 0–2: ключевые механизмы отсутствуют/не работают; 3–4: частичная реализация с серьёзными дефектами; 5–6: работоспособная основа с существенными ограничениями; 7–8: зрелая реализация с локальными недостатками; 9–10: полнота подтверждена сильными проверками. Итог = сумма(оценка × вес). Непроверенное не считать успешным; явно показывать ограничения уверенности. Наличие P1 в доступе или целостности данных блокирует рекомендацию промышленного запуска независимо от среднего балла.

## Результат

Сохрани отчёт с датой, областью проверки, результатами команд, таблицей оценок и приоритетным списком подтверждённых проблем. Отдельно перечисли непроверенное. Дай короткий вердикт и порядок устранения проблем. Никаких утверждений о внешней безопасности, производительности под нагрузкой или юридической корректности подписей без соответствующих проверок.
